## Об этом документе

=================

В этом документе описывается рантайм ARC/ORC в Nim, который
больше не использует классические алгоритмы GC, а основан на деструкторах
и семантике перемещения (move semantics). Преимущества в том, что программы на Nim
становятся менее зависимыми от размеров кучи и проще писаться для
эффективного использования многопроцессорных систем. Дополнительный бонус —
файлы, сокеты и подобные ресурсы можно обрабатывать без явных вызовов `close`.

Цель документа — дать точную спецификацию того, как работают
семантика перемещения и деструкторы в Nim.

## Мотивирующий пример

===================

С помощью описанных здесь механизмов можно реализовать собственную `seq`:

```nim test
type
  myseq*[T] = object
    len, cap: int
    data: ptr UncheckedArray[T]

proc `=destroy`*[T](x: myseq[T]) =
  if x.data != nil:
    for i in 0..<x.len: `=destroy`(x.data[i])
    dealloc(x.data)

proc `=wasMoved`*[T](x: var myseq[T]) =
  x.data = nil

proc `=trace`[T](x: var myseq[T]; env: pointer) =
  # `=trace` позволяет сборщику циклов `--mm:orc`
  # понимать как трассировать граф объектов.
  if x.data != nil:
    for i in 0..<x.len: `=trace`(x.data[i], env)

proc `=copy`*[T](a: var myseq[T]; b: myseq[T]) =
  # ничего не делать при самоприсваивании:
  if a.data == b.data: return
  `=destroy`(a)
  `=wasMoved`(a)
  a.len = b.len
  a.cap = b.cap
  if b.data != nil:
    a.data = cast[typeof(a.data)](alloc(a.cap * sizeof(T)))
    for i in 0..<a.len:
      a.data[i] = b.data[i]

proc `=dup`*[T](a: myseq[T]): myseq[T] {.nodestroy.} =
  # оптимизированная версия `=wasMoved(tmp); `=copy(tmp, src)`
  result = myseq[T](len: a.len, cap: a.cap, data: nil)
  if a.data != nil:
    result.data = cast[typeof(result.data)](alloc(result.cap * sizeof(T)))
    for i in 0..<result.len:
      result.data[i] = `=dup`(a.data[i])

proc `=sink`*[T](a: var myseq[T]; b: myseq[T]) =
  # перемещающее присваивание (опционально).
  `=destroy`(a)
  a.len = b.len
  a.cap = b.cap
  a.data = b.data

proc add*[T](x: var myseq[T]; y: sink T) =
  if x.len >= x.cap:
    x.cap = max(x.len + 1, x.cap * 2)
    x.data = cast[typeof(x.data)](realloc(x.data, x.cap * sizeof(T)))
  x.data[x.len] = y
  inc x.len

proc `[]`*[T](x: myseq[T]; i: Natural): lent T =
  assert i < x.len
  x.data[i]

proc `[]=`*[T](x: var myseq[T]; i: Natural; y: sink T) =
  assert i < x.len
  x.data[i] = y

proc createSeq*[T](elems: varargs[T]): myseq[T] =
  result = myseq[T](
    len: elems.len,
    cap: elems.len,
    data: cast[typeof(result.data)](alloc(result.cap * sizeof(T))))
  for i in 0..<result.len: result.data[i] = elems[i]

proc len*[T](x: myseq[T]): int {.inline.} = x.len
```

# Хуки для отслеживания времени жизни

Управление памятью для стандартных типов `string` и `seq`, а также других
стандартных коллекций в Nim выполняется с помощью так называемых
"lifetime-tracking hooks" — специальных операторов, привязанных к типу
(type bound operators).

Для каждого (обобщённого или конкретного) объектного типа `T` существует
6 разных хуков, которые вызываются неявно компилятором. (Слово "hook" здесь
не означает динамической привязки; вызовы статически связаны и могут быть
инлайнированы.)

## Хук `=destroy`

Хук `=destroy` освобождает связанный с объектом ресурс и другие связанные
ресурсы. Переменные уничтожаются через этот хук при выходе из области
видимости или перед возвращением из рутин.

Подпись хука для типа `T` должна быть:

```nim
proc `=destroy`(x: T)
```

Обычно `=destroy` сначала проверяет, был ли объект перемещён:

```nim
proc `=destroy`(x: T) =
  # first check if 'x' was moved to somewhere else:
  if x.field != nil:
    freeResource(x.field)
```

Деструктор не должен выбрасывать исключения — неявно ему добавляется
аннотация `.raises: []`. Для обратной совместимости компилятор выдает
предупреждение, если деструктор всё же бросает исключение.

## Хук `=wasMoved`

Хук `=wasMoved` переводит объект в состояние, означающее для деструктора,
что ему нечего освобождать.

Подпись хука для типа `T` должна быть:

```nim
proc `=wasMoved`(x: var T)
```

Типичная реализация просто зануляет указатель внутри объекта:

```nim
proc `=wasMoved`(x: var T) =
  x.field = nil
```

## Хук `=sink`

Хук `=sink` перемещает объект: ресурсы крадутся у источника и передаются
приёмнику. Гарантируется, что деструктор источника не освободит ресурсы,
поскольку объект приводится к значению по умолчанию (wasMoved).
Если `=sink` не предоставлен, компилятор использует сочетание `=destroy`
и `copyMem`. Обычно достаточно реализовать `=destroy` и `=copy` — компилятор
позаботится о остальном.

Подпись хука для типа `T` должна быть:

```nim
proc `=sink`(dest: var T; source: T)
```

Общая схема `=sink`:

```nim
proc `=sink`(dest: var T; source: T) =
  `=destroy`(dest)
  wasMoved(dest)
  dest.field = source.field
```

Примечание: `=sink` не обязан проверять самоприсваивания — это обсуждается
ниже.

## Хук `=copy`

Обычное присваивание в Nim концептуально копирует значения. Хук `=copy`
вызывается для присваиваний, которые не могут быть преобразованы в `=sink`.

Подпись хука для типа `T` должна быть:

```nim
proc `=copy`(dest: var T; source: T)
```

Пример общего шаблона:

```nim
proc `=copy`(dest: var T; source: T) =
  # защититься от самоприсваивания:
  if dest.field != source.field:
    `=destroy`(dest)
    wasMoved(dest)
    dest.field = duplicateResource(source.field)
```

Хук `=copy` может быть помечен pragma `{.error.}`, тогда любое присваивание,
которое привело бы к копированию, запрещается на этапе компиляции:

```nim
proc `=copy`(dest: var T; source: T) {.error.}
```

## Хук `=trace`

Пользовательский контейнерный тип может поддерживать сборщик циклов `--mm:orc`
через хук `=trace`. Если `=trace` не реализован, циклические структуры,
созданные с использованием контейнера, могут приводить к утечкам, но
безопасность памяти не нарушается.

Подпись хука для типа `T` должна быть:

```nim
proc `=trace`(dest: var T; env: pointer)
```

Параметр `env` используется ORC для отслеживания внутреннего состояния и
должен передаваться при вызове встроенного `=trace`.

Обычно `=trace` требуется только если есть пользовательский `=destroy`,
который вручную освобождает ресурсы, и существует риск циклических ссылок
внутри этих ресурсов — тогда `--mm:orc` должен иметь возможность разорвать
и собрать такие циклические структуры. Наблюдается проблема: порядок
создания автоматически сгенерированных `=destroy`/`=trace` может конфликтовать.
Обход — форвардное объявление второго хука.

Общий шаблон использования `=destroy` с `=trace`:

```nim
type
  Test[T] = object
    size: Natural
    arr: ptr UncheckedArray[T] # raw pointer field

proc makeTest[T](size: Natural): Test[T] = # custom allocation...
  Test[T](size: size, arr: cast[ptr UncheckedArray[T]](alloc0(sizeof(T) * size)))

proc `=destroy`[T](dest: Test[T]) =
  if dest.arr != nil:
    for i in 0 ..< dest.size: dest.arr[i].`=destroy`
    dealloc dest.arr

proc `=trace`[T](dest: var Test[T]; env: pointer) =
  if dest.arr != nil:
    # trace the `T`'s which may be cyclic
    for i in 0 ..< dest.size: `=trace`(dest.arr[i], env)

# following may be other custom "hooks" as required...
```

Примечание: хук `=trace` (используемый только `--mm:orc`) более экспериментален
и менее отполирован, чем другие хуки.

## Хук `=dup`

Хук `=dup` дублирует объект. `=dup(x)` можно рассматривать как оптимизацию,
заменяющую `wasMoved(dest); =copy(dest, x)`.

Подпись хука должна быть:

```nim
proc `=dup`(x: T): T
```

Пример:

```nim
type
  Ref[T] = object
    data: ptr T
    rc: ptr int

proc `=dup`[T](x: Ref[T]): Ref[T] =
  result = x
  if x.rc != nil:
    inc x.rc[]
```

# Семантика перемещения (Move semantics)

"Move" можно рассматривать как оптимизированную операцию копирования. Если
источник копии далее не используется, копирование можно заменить перемещением.
В документе используется обозначение `lastReadOf(x)`, означающее, что `x`
не используется дальше. Это вычисляется статическим анализом потока управления
или может быть явно указано через `system.move`.

Можно проверить, может ли быть выполнено перемещение, с помощью `system.ensureMove`.
`move` принудительно выполняет перемещение и вызывает `=wasMoved`, тогда как
`ensureMove` — аннотация без выполнения времени исполнения; если компилятор
не может доказать безопасность перемещения, `ensureMove` выдаёт статическую ошибку.

Пример:

```nim
proc main(normalParam: string; sinkParam: sink string) =
  var x = "abc"
  # valid:
  let valid = ensureMove x
  # invalid:
  let invalid = ensureMove normalParam
  # valid:
  let alsoValid = ensureMove sinkParam
```

# Swap

Потребность проверки самоприсваиваний и уничтожения предыдущих объектов в
`=copy`/`=sink` указывает на то, что `system.swap` следует рассматривать
как встроенную примитивную операцию, которая просто меняет все поля объектов
через `copyMem` или подобный механизм. Иначе `swap(a,b)` не реализуется как
`let tmp = move(b); b = move(a); a = move(tmp)`.

Последствия:

- Объекты с указателями на один и тот же объект не поддерживаются Nim'ом —
  иначе после swap объекты окажутся в неконсистентном состоянии.
- Seq'и могут использовать `realloc` в реализации.

# Sink-параметры

Чтобы переместить переменную в коллекцию, обычно используются `sink`-параметры.
Локация, переданная в `sink`, не должна использоваться дальше — это гарантируется
статическим анализом потока управления. Если анализ не может доказать, что это
последнее использование, выполняется копирование и копия передаётся в sink.

Параметр sink может быть потреблён внутри тела процедуры, но не обязан.
Это позволяет, например, сигнатуры вида `proc put(t: var Table; k: sink Key, v: sink Value)`
без дополнительных перегрузок; `put` может не передавать владение `k`, если
ключ уже есть в таблице. Sink-параметры дают аффинную систему типов, а не
линейную.

Анализ ограничен локальными переменными; поля объектов и кортежей рассматриваются
как отдельные сущности.

Пример:

```nim
proc consume(x: sink Obj) = discard "no implementation"

proc main =
  let tup = (Obj(), Obj())
  consume tup[0]
  # ok, только tup[0] был потреблён, tup[1] всё ещё жив:
  echo tup[1]
```

Иногда требуется явно `move` значение в его финальную позицию:

```nim
proc main =
  var dest, src: array[10, string]
  # ...
  for i in 0..high(dest): dest[i] = move(src[i])
```

Реализация может, но не обязана, вводить дополнительные оптимизации перемещений.

# Вывод sink-параметров (Sink parameter inference)

Текущая реализация может делать ограниченную форму вывода sink-параметров.
Её нужно включать через `--sinkInference:on`, например в командной строке или
с помощью pragma `push`.

Для включения в части кода можно использовать `{.push sinkInference: on.}` ... `{.pop.}`.

pragma `.nosinks` позволяет отключить вывод для отдельной процедуры:

```nim
proc addX(x: T; child: T) {.nosinks.} =
  x.s.add child
```

Детали алгоритма вывода в настоящее время не документированы.

# Правила переписывания (Rewrite rules)

Примечание: доступны две допустимые стратегии реализации:

1. Сгенерированный `finally` может быть единым блоком, охватывающим всё тело рутины.
2. Сгенерированный `finally` охватывает окружающую область.

Текущая реализация следует стратегии (2), то есть ресурсы уничтожаются при
выходе из области видимости.

Примеры правил переписывания (сокращённо):

```
var x: T; stmts
---------------             (destroy-var)
var x: T; try stmts
finally: `=destroy`(x)

g(f(...))
------------------------    (nested-function-call)
g(let tmp;
bitwiseCopy tmp, f(...);
tmp)
finally: `=destroy`(tmp)

x = f(...)
------------------------    (function-sink)
`=sink`(x, f(...))

x = lastReadOf z
------------------          (move-optimization)
`=sink`(x, z)
`=wasMoved`(z)

v = v
------------------   (self-assignment-removal)
discard "nop"

x = y
------------------          (copy)
`=copy`(x, y)

f_sink(g())
-----------------------     (call-to-sink)
f_sink(g())

f_sink(notLastReadOf y)
--------------------------     (copy-to-sink)
(let tmp = `=dup`(y);
f_sink(tmp))

f_sink(lastReadOf y)
-----------------------     (move-to-sink)
f_sink(y)
`=wasMoved`(y)
```

# Конструкция создания объектов и массивов

Создание объектов и массивов рассматривается как вызов функции с `sink`-параметрами.

# Удаление деструктора (Destructor removal)

`=wasMoved(x)` сразу перед `=destroy(x)` аннулируют друг друга. Реализация
рекомендуется использовать это для оптимизации размера кода и эффективности.
Текущая реализация такой оптимизацией пользуется.

# Самоприсваивания

`=sink` в сочетании с `=wasMoved` может обрабатывать самоприсваивания, но это
тонкий момент.

Простые случаи `x = x` не могут быть заменены на `=sink(x, x); =wasMoved(x)`,
потому что это приведёт к потере значения `x`. Решение: простые самоприсваивания
в виде

- символы: `x = x`
- доступ к полю: `x.f = x.f`
- доступ к массиву/последовательности/строке с индексом, известным в компиляции: `x[0] = x[0]`

преобразуются в пустое выражение (no-op). Компилятор может оптимизировать
и другие случаи.

Сложный случай напоминает `x = f(x)`, например `x = select(rand() < 0.5, x, y)`.

Пример преобразования показан в оригинале и демонстрирует корректность.

# Тип lent

`proc p(x: sink T)` означает, что `p` принимает владение `x`. Чтобы избежать
лишних пар создание/копирование <-> уничтожение, тип возвращаемого значения
процедуры может быть аннотирован как `lent T`. Это полезно для "геттеров",
которые хотят вернуть неизменяемый доступ к контейнеру.

`lent T` подобен скрытому указателю `var T`. Компилятор доказывает, что указатель
не переживает своё происхождение, и для выражений типа `lent T` или `var T`
вызов деструктора не вставляется.

Примеры использования `lent` показаны в оригинале.

# Прагма cursor

В режимах `--mm:arc|orc` тип `ref` реализуется через те же "хуки" и
через подсчёт ссылок. Это означает, что циклические структуры не могут быть
освобождены немедленно (`--mm:orc` содержит сборщик циклов). С помощью
прагмы `cursor` можно декларативно разрывать циклы:

```nim
type
  Node = ref object
    left: Node # owning ref
    right {.cursor.}: Node # non-owning ref
```

Это не соответствует `weak_ptr` из C++: поле с `cursor` просто не участвует
в подсчёте ссылок и является «сырым» указателем без проверок времени выполнения.

`cursor` также снижает накладные расходы при итерации по связанным структурам,
так как избегает операций подсчёта ссылок.

`cursor` предотвращает пары создания/уничтожения объектов и может быть полезен
в других контекстах; альтернативой являются сырые указатели (`ptr`), которые
более трудны в использовании и опаснее для развития компилятора.

# Вывод cursor / элиминация копирования (Cursor inference / copy elision)

Текущая реализация выполняет вывод `cursor` — форму элиминации копирования.
Идея: в присваивании `dest = src` материализация полного копирования требуется
только если `dest` или `src` изменяются позже. Если `dest` — локальная переменная
и `src` — расположение, производное от формального параметра и не мутируется,
можно применить copy-on-write анализ во время компиляции.

Это позволяет писать «заёмные» представления без явных указателей.

# Лифтинг хуков (Hook lifting)

Хуки для типа кортежа `(A, B, ...)` генерируются путём подъёма хуков составляющих
типов `A`, `B`, ... к типу кортежа. Копирование `x = y` реализуется как
`x[0] = y[0]; x[1] = y[1]; ...`, аналогично для `=sink` и `=destroy`.

Другие составные типы по значению, такие как `object` и `array`, обрабатываются
соответственно. Для `object` сгенерированные хуки можно переопределить, что
иногда нужно для альтернативной, более эффективной, или неглубокой реализации
прохода по структуре.

# Генерация хуков (Hook generation)

Возможность переопределить хук приводит к проблеме порядка фаз:

```nim
type
  Foo[T] = object

proc main =
  var f: Foo[int]
  # error: destructor for 'f' called here before
  # it was seen in this module.

proc `=destroy`[T](f: Foo[T]) =
  discard
```

Решение: объявлять `proc `=destroy`[T](f: Foo[T])` до места использования.
Компилятор генерирует неявные хуки для типов в стратегических местах, чтобы
обнаруживать поздние определения хуков. Эти места:

- В конструкциях `let/var x = ...` (привязка)
- В `x = ...` (присваивание)
- В `f(...)` (вызов функции)
- Для каждого sink-параметра `x: sink T` генерируются хуки для `typeof(x)`.

# Прагма nodestroy

Экспериментальная pragma `nodestroy` предотвращает внедрение хуков. Это можно
использовать для специализации обхода объектов, чтобы избежать глубокой рекурсии:

```nim test
type Node = ref object
  x, y: int32
  left, right: Node

type Tree = object
  root: Node

proc `=destroy`(t: Tree) {.nodestroy.} =
  var s: seq[Node] = @[t.root]
  while s.len > 0:
    let x = s.pop
    if x.left != nil: s.add(x.left)
    if x.right != nil: s.add(x.right)
    `=dispose`(x)
  `=destroy`(s)
```

Как видно, решение не идеально и требует улучшений.

# Copy on write

Строковые литералы реализованы как "copy on write". При присваивании литерала
строки переменной копия не создаётся — переменная ссылается на литерал.
Копирование откладывается до первой записи.

Например:

```nim
var x = "abc"  # no copy
var y = x      # no copy
y[0] = 'h'     # copy
```

Альтернатива `addr x` ломает эту абстракцию, поэтому перед взятием адреса
нужно вызвать `prepareMutation`.

Пример:

```nim
var x = "abc"
var y = x

prepareMutation(y)
moveMem(addr y[0], addr x[0], 3)
```
