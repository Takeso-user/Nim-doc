# Введение

В этом документе описываются встроенные в компилятор Nim `documentation generation tools` —
инструменты генерации документации, которые могут создавать HTML, LaTeX и JSON
из исходных файлов и проектов на Nim. Сгенерированная документация включает
зависимости модулей (`import`), любые верхнего уровня комментарии документации (`##`) и
экспортируемые символы (`*`), включая процедуры, типы и переменные.

| command       | output format |
| ------------- | ------------- |
| `nim doc`     | `.html` HTML  |
| `nim doc2tex` | `.tex` LaTeX  |
| `nim jsondoc` | `.json` JSON  |

Nim также может генерировать HTML и LaTeX из входных Markdown и
RST (reStructuredText) файлов — это удобно для написания самостоятельных
документов, таких как руководства пользователя и технические спецификации.
См. документ «Nim-flavored Markdown and reStructuredText» для подробностей
и раздел «Command line usage» для полного списка поддерживаемых команд.

## Быстрый старт

Генерация HTML-документации для файла:

```cmd
nim doc <filename>.nim
```

Генерация HTML-документации для всего проекта:

```cmd
# delete any htmldocs/*.idx file before starting
nim doc --project --index:on --git.url:<url> --git.commit:<tag> --outdir:htmldocs <main_filename>.nim
# this will generate html files, a theindex.html index, css and js under `htmldocs`
# See also `--docroot` to specify a relative root.
# to get search (dochacks.js) to work locally, you need a server otherwise
# CORS will prevent opening file:// urls; this works:
python3 -m http.server 7029 --directory htmldocs
# When --outdir is omitted it defaults to $projectPath/htmldocs,
# or `$nimcache/htmldocs` with `--usenimcache` which avoids clobbering your sources;
# and likewise without `--project`.
# Adding `-r` will open in a browser directly.
# Use `--showNonExports` to show non-exported fields of an exported type.
```

## Комментарии документации

Любые комментарии, предваряемые двойным хешем (`##`), интерпретируются как
документация. Комментарии парсятся как RST (см. reference), что даёт авторам
модулей Nim возможность легко генерировать богатую форматированную
документацию, просто документируя код. Также поддерживается базовый синтаксис Markdown
внутри таких комментариев.

Пример:

```nim
type Person* = object
  ## This type contains a description of a person
  name: string
  age: int
```

Вывод:

```
Person* = object
  name: string
  age: int

This type contains a description of a person
```

Комментарии к полям можно добавлять так:

```nim
var numValues: int ## \
  ## `numValues` stores the number of values
```

Без `*` после имени типа документация для него не будет сгенерирована —
документация создаётся только для экспортируемых типов/процедур/и т.д.

Рекомендуется добавлять ровно **один** пробел после `##` для читаемости —
этот пробел будет удалён при парсинге и не повлияет на RST-форматирование.

> **Примечание**: Базовый уровень отступа внутри блока документации может быть
> произвольным — он определяется смещением первого не‑пробельного символа в
> комментарии. После этого отступ **должен** быть согласован для последующих строк
> в том же комментарии. Если необходимо добавить дополнительный отступ в
> начале (например, для синтаксиса блочного цитирования RST), используйте
> обратный слэш `\` перед ним.

## Структурирование выходных директорий

Директория по умолчанию для выходных файлов задаётся переключателем
`--outdir:OUTDIR` (по умолчанию `htmldocs` в каталоге обрабатываемого файла).

Существуют 2 базовых варианта хранения сгенерированных HTML-файлов:

1. Сложная иерархия, когда используется `--project` — повторяет структуру
   проекта внутри `--outdir`. Такой режим удобен для проектов с одним
   главным модулем — конфликтов имён не будет.
2. Плоская структура — скрипт пользователя обходит входные файлы и
   вызывает `nim doc` с `--outdir`, складывая все HTML/`.idx` в одну папку.

   В этом случае следите, чтобы не было файлов с одинаковыми базовыми именами
   (например, `x.nim` и `x.md`) — иначе возникнет конфликт для `x.html`.

> **Совет**: Для организации выходных директорий и избежания конфликтов имён
> можно разделить проект на пакеты, генерируя для каждой части свою `--outdir`.

## Index files

Файлы `.idx` используются для двух целей:

1. удобная кросс‑ссылка между `.nim` и/или `.md`/`.rst` файлами (Nim external referencing);
2. создание общего индекса проекта для поиска символов и ключевых слов (Buildindex).

## Типы документов

### Пример входного Nim-файла

Следующий пример сгенерирует документацию для демонстрационного модуля
`doc/docgen_sample.nim` (см. оригинал для содержимого примера).

Все приведённые команды сохраняют вывод в директорию `htmldocs` рядом
с обрабатываемым файлом; для примера вывод будет в `doc/htmldocs`.

### HTML

Генерация HTML осуществляется командой `doc`. Она принимает либо один
`.nim` файл (порождает один `.html` файл с тем же базовым именем), либо
несколько `.nim` файлов (порождает несколько `.html` и, опционально, файл индекса).

Команда:

```cmd
nim doc docgen_sample.nim
```

Частичный вывод (пример):

```
...
proc helloWorld(times: int) {.raises: [], tags: [].}
...
```

Полный пример вывода смотрите в `docgen_sample.html`.

### LaTeX

LaTeX удобно конвертировать в PDF для оффлайнового чтения или печати.

Команда:

```cmd
nim doc2tex docgen_sample.nim
cd htmldocs
xelatex docgen_sample.tex
xelatex docgen_sample.tex
# Обычно `xelatex` запускают 2 (или более) раз для корректной генерации ссылок.
```

### JSON

Генерация JSON осуществляется командой `jsondoc`. Она принимает `.nim` файл
и выводит соответствующий `.json` файл.

Команда:

```cmd
nim jsondoc docgen_sample.nim
```

Вывод (пример):

```json
{
  "orig": "docgen_sample.nim",
  "nimble": "",
  "moduleDescription": "This module is a sample",
  "entries": [
    {
      "name": "helloWorld",
      "type": "skProc",
      "line": 5,
      "col": 0,
      "description": "Takes an integer and outputs as many &quot;hello world!&quot;s",
      "code": "proc helloWorld(times: int) {.raises: [], tags: [].}"
    }
  ]
}
```

Примечание: старая команда `jsondoc` была переименована в `jsondoc0` —
`jsondoc` выводит JSON без pretty-print, а `jsondoc0` — форматированный JSON.

## Простые ссылки в документации

Можно использовать обычный синтаксис Markdown/RST для ручных ссылок на
символы Nim через HTML‑якоря, но Nim предоставляет автоматический механизм
разрешения ссылок внутри `.nim` и `.md/.rst` файлов. Такие ссылки будут
проверяться на существование — при битой ссылке будет выдано предупреждение.

Nim рассматривает и `.md/.rst` документы, и модули `.nim` (в их части комментариев)
как документы на одном уровне; поэтому направления ссылок между ними
одинаковы.

Ссылка на `proc f` в Markdown может выглядеть как `Ref. [proc f]` или просто `[f]`.
В RST эквивалент — `` Ref. `proc f`_ ``.

### Nim локальные ссылки

Можно ссылаться на идентификаторы Nim внутри их `.nim` файла (или в
включаемом RST). Это относится к любым экспортируемым символам — `proc`, `const`, `iterator` и т.д.

Формат ссылки отображает текст ссылки, а цель (anchor) ставится на соответствующий
Nim символ.

Пример для `const pi* = 3.14`:

A. неквалифицированно: `pi_`

B. квалифицированно: `` `const pi`_``

Для рутин есть более вариативные формы — короткие и длинные (с параметрами).
В документации описаны допустимые варианты (см. оригинал для всех подробностей).

> **Предупреждение**: может возникать неоднозначность при разрешении ссылок из‑за
> конфликтов с RST-якорями или с другими Nim-символами (например, `proc` и `template` с тем же именем).
> Компилятор сообщает о неоднозначностях и выбирает приоритетный якорь.

## Nim внешние ссылки (External referencing)

Nim symbols сохраняются в `.idx` файлах, поэтому их нужно сгенерировать
заранее и подключить через директиву `.. importdoc::`. Параметры `importdoc` —
список модулей или Markdown/RST документов через запятую.

Опция `--index:only` генерирует только `.idx` без попытки сгенерировать
HTML/LaTeX.

Для `.nim` модулей есть 2 подхода:

1. использовать `--project`, который генерирует `.idx` для всего пакета, но
   если вы вызываете `importdoc` для верхних модулей, их `.idx` ещё могут не
   быть созданы — сгенерируйте **все** нужные `.idx` заранее.
2. или запустить `nim doc --index:only <module.nim>` для всех модулей проекта,
   затем отдельные `nim doc` для вывода HTML.

Для `.md`/`.rst` документов пункт 2 — единственный вариант.

Если `importdoc` не найдёт `.idx`, будет выведена ошибка. Важно помнить:

- все относительные пути в `importdoc` относятся к содержимому `OUTDIR`, а не
  к структуре проекта на диске;
- `importdoc` ищет `.idx` в директории `--outdir` (по умолчанию `htmldocs`);
- `.html` и `.idx` должны всегда выводиться в одну и ту же директорию —
  проверьте параметры и убедитесь, что оба запуска используют одинаковые опции.

Кратко, для двух стратегий структурирования выходных директорий различаются
и опции компиляции:

1. Сложная иерархия (`--project`): пути в `OUTDIR` соответствуют структуре проекта.
2. Плоская структура: пути в `importdoc` должны соответствовать размещению файлов в `OUTDIR`.

Если вам временно не нужна корректная резолюция внешних ссылок, используйте
`--noImportdoc` — будут сгенерированы только предупреждения об нерешённых ссылках.

## Связанные опции

### Project switch

```cmd
nim doc --project filename.nim
```

Рекурсивно генерирует документацию для всех модулей, импортируемых входным
модулем и принадлежащих пакету Nimble, к которому относится `filename.nim`.
Также генерируются `.idx` и `theindex.html`.

### Index switch

```cmd
nim doc --index:on filename.nim
```

Генерирует `.idx` файл со всеми экспортируемыми символами модуля. Файл
линео-ориентированный — символы разделены табуляцией (символы `\n` и `\t`
должны быть экранированы). См. раздел «Index (idx) file format» для деталей.

> Примечание: `--index` влияет только на создание `.idx`. Пользовательский HTML
> индекс создаётся командой `buildIndex`.

### Buildindex

После генерации `.idx` файлов для модуля(ей) можно выполнить:

```cmd
nim buildIndex -o:path/to/htmldocs/theindex.html path/to/htmldocs
```

Эта команда пройдётся по всем `.idx` в указанной директории и создаст
`theindex.html`.

### See source

```cmd
nim doc --git.url:<url> filename.nim
```

С опцией `--git.url` ссылка «See source» появится под каждым документированным
элементом и укажет на реализацию в указанном репозитории (GitHub-подобный URL).
Опция `--git.commit` позволяет указать ветку/тег/хеш вместо значения по умолчанию
(`devel` в `config/nimdoc.cfg`).

URL-генерация по умолчанию совместима с GitHub; при необходимости отредактируйте
`config/nimdoc.cfg` и `doc.item.seesrc`.

## Другие входные форматы

Компилятор поддерживает RST (reStructuredText) через команды `rst2html` и `rst2tex`.
Документы могут быть написаны в диалекте RST, который добавляет подсветку
исходников с помощью `.. code-block:: nim`.

См. «Markdown and RST markup languages» для примеров и поддерживаемых возможностей.

## Генерация HTML-якорей

При запуске `rst2html` секциям в RST документе назначаются якоря. Обычно якорь
получается приведением заголовка к нижнему регистру и заменой пробелов на дефисы,
но точную строку можно посмотреть в оглавлении.

При генерации API-документации `nim doc` некоторым символам может быть назначено
несколько якорей: числовой идентификатор (зависит от позиции в файле) и более
читаемое имя, основанное на сигнатуре.

Если несколько совпадений в одном HTML-файле ведут на один plain-name якорь,
браузер перейдёт к первому. Чтобы отличать остальные, используйте сложные имена.

| Callable type  | Suffix  |
| -------------- | ------- |
| `proc`, `func` | (empty) |
| `macro`        | `.m`    |
| `method`       | `.e`    |
| `iterator`     | `.i`    |
| `template`     | `.t`    |
| `converter`    | `.c`    |

Соответствие типов суффиксов формируется процедурой `complexName` в
`compiler/docgen.nim`.

## Index (idx) file format

Файлы с расширением `.idx` генерируются при использовании Index switch вместе
с командами генерации документации. Они держат в себе интересующие символы и
их HTML-ссылки, чтобы позднее объединить их в единый индекс с помощью
`mergeIndexes()`.

`.idx` — это построчный табуляцией-разделённый формат. Каждая строка содержит
6 полей:

0. Тег‑дискриминатор (тип записи): `markupTitle`, `nimTitle`, `heading`, `idx`, `nim`, `nimgrp`.
1. Обязательный индексируемый термин (может содержать кавычки по правилам Nim).
2. Базовое имя файла плюс якорь (например `algorithm.html#*,int,SortOrder`).
3. Опциональная читаемая строка для отображения; если пустая — будет использоваться термин.
   Отступы в начале означают, что запись — это элемент оглавления (TOC).
4. Опциональное поле — заголовок или описание ссылки (тултип).
5. Номер строки, где запись была определена.

Генераторы различают документы, сгенерированные из `.nim` и из `.md`/`.rst`
по тегу в первой строке файла (`nimTitle` или `markupTitle`).
